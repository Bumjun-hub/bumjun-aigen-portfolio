02 / PROBLEM SOLVING

구현보다 중요한 것은
판단과 개선의 과정

CASE 01 · Project S

추천 계산 로직의
책임 분리

추천 규칙이 서비스 로직에 함께 있으면 조건이 변경될 때 영향 범위가 커질 수 있다고 판단했습니다. 계산 책임을 RecommendationCalculator로 분리하고 추천 규칙을 독립적으로 다룰 수 있도록 구조화했습니다.

핵심 배움: 작동하는 코드에서 더 나아가, 바뀔 수 있는 기준과 역할을 구분하는 설계가 필요합니다.

CASE 02 · Project S

예상하지 못한
데이터 저장 충돌

기준 의류 정보를 수정하는 과정에서 고유 제약조건 충돌이 발생했습니다. 단순 삭제·재삽입 방식만 유지하지 않고, JPA와 데이터베이스의 저장 흐름을 고려해 기존 엔티티를 갱신하는 접근으로 변경했습니다.

핵심 배움: 오류 메시지를 아는 것과 설계의 가정을 다시 검토하는 것은 전혀 다른 일입니다.

CASE 03 · NeighFund

다시 읽고,
다시 고친 코드

첫 프로젝트에서는 화면과 기능 구현에 집중했지만, 시간이 지난 뒤 API 호출이 페이지별로 흩어져 있고 상태 관리 방식이 일관되지 않다는 점을 확인했습니다. 개인 리팩터링을 진행하며 공통 API 클라이언트와 React Query 기반 서버 상태 관리로 구조를 정리했습니다.

핵심 배움: 프로젝트 완료가 학습의 끝은 아닙니다. 이전의 선택을 다시 평가하고 더 나은 설계를 시도할 수 있어야 합니다.

03 / AIGEN VALUES

도전가 · 성취가 · 혁신가

↗

도전가

처음부터 끝까지 직접 시도했습니다. Project S에서 기획, 설계, 구현, 테스트와 배포까지 혼자 진행하며 모르는 기술을 배우고 적용했습니다.

◎

성취가

아이디어를 동작하는 결과물로 만들었습니다. 핵심 사용자 흐름을 연결하고 테스트를 작성하며, 완성된 기능을 근거로 설명하고 노력했습니다.

↻

혁신가

익숙한 방식에 질문했습니다. 기존 의류를 활용한 새로운 비교 방식을 제안하고, 기존 프로젝트의 코드 구조를 다시 개선했습니다.

04 / WHAT'S NEXT

다음 도전은, AI를
사용자에게 도움이 되는 서비스로.

저는 AI 모델을 연구하는 것 자체보다, AI 기술을 실제 서비스에 연결해 사용자의 문제를 해결하는 개발자가 되고 싶습니다. 웹 서비스 개발에서 쌓은 설계·구현·검증 경험을 바탕으로 AIGEN에서 새로운 문제를 찾고, AI 기술을 도구로 활용하되 결과의 신뢰성과 사용자 경험을 함께 검토하고 싶습니다.

문제와 사용자 이해

사용자가 실제로 겪는 불편을 인터뷰와 사용 흐름으로 확인하고, AI가 도울 지점을 구분합니다.

02 · Build

AI 서비스 프로토타입

03 · Validate

정확성과 사용성 검증

근거 없는 응답, 개인정보, 지연 시간과 비용을 살피고 평가 결과를 바탕으로 기능을 개선합니다.
